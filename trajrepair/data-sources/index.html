Provenance boundary

Inherited versus constructed

This distinction should be explicit in the paper. TrajRepair-Bench does not claim authorship of the upstream tasks. Its contribution is the transformation of real failed runs into reproducible, repairable, execution-validated instances.

Inherited

Upstream task package

Task description, clean environment definition, official verifier semantics, and upstream reference assets used for dataset construction.

→
Observed

Organic failed run

Model reasoning, tool actions, terminal observations, the executable action sequence, and the upstream failure verdict.

→
Constructed by us

Repair instance

Normalized action list, reproduced failure, leak-audited failure scene, augmented checks, split metadata, clean-replay judge, and edit metrics.

Construction protocol

From failed run to repair benchmark

Admission depends on executable evidence. Every instance must preserve the original task semantics, reproduce the source failure, expose a faithful but leak-free failure scene, and support clean replay of a submitted action list.

Extract

Project reasoning, terminal actions, and observations into a normalized R/P/O trajectory and executable action list.

Reproduce

Replay the original action list from the official clean environment. Keep the instance only when the failure is reproduced.

Snapshot

Capture the post-failure container for diagnosis, then remove tests, oracle material, and authoring artifacts.

Augment

Add executable goal, enabler, and constraint checks derived from the specification and upstream assets.

Select

Deduplicate by failure signature or repair similarity, apply quality gates, and freeze the development/test split.

Agent-visible evidence

  • Original task description
  • Full failed R/P/O trajectory
  • Numbered original action list
  • Explorable failure-scene container
  • Submission schema and scoring rules

Withheld evaluation assets

  • Official tests and verifier internals
  • Reference solution or repair oracle
  • Localization truth and construction evidence
  • Private augmented-check implementation
  • Judge results before final submission

Quality and evaluation

Execution is the oracle

A repair system submits a complete revised action list. The evaluator computes the diff automatically, replays the list from a clean environment, and reports both upstream and strengthened correctness verdicts.

Failure fidelity

All 285 source action lists have corresponding replayed failure scenes. Harbor records preserve a zero reward on all 126 selected failures.

Official verdict

Repair@1 (official) uses the task's inherited official verifier and remains the externally comparable result.

Strict verdict

Repair@1 (strict) requires both the official verifier and augmented specification checks to pass.

Repair cost

Replaced, deleted, and inserted actions are derived from the old/new list alignment. Correctness remains primary.

Augmented-check accounting. Harbor contributes 1,421 checkpoint-instance evaluations from 337 unique probes across 29 task catalogs. The Terminal lane contains 496 task-level checkpoints across 61 tasks, including 228 directly executable end-state probes. These are different counting units and should not be added as if they were the same statistic.

Paper-ready wording

Data sources paragraph

This paragraph is deliberately conservative: it distinguishes upstream material from our transformations and uses the current 10-family counting convention.

TrajRepair-Bench v2 aggregates organic failed agent executions from two acquisition lanes. The Terminal-Bench lane contains 159 failures over 61 tasks, generated locally by seven model configurations using mini-swe-agent and OpenHands. The Harbor lane contains 126 failures over 29 tasks, selected from the public audit trajectories of Harbor-Index 1.0 and generated by nine model configurations under Terminus-2. Across both lanes, the resulting pool contains 285 execution-verified failures over 90 tasks from ten upstream benchmark families. We normalize each run into a reasoning/action/observation trajectory and an executable action list, replay the original list from the official clean environment to reproduce the failure, and snapshot a leak-audited post-failure container for diagnosis. A repair system submits a complete revised action list, which is replayed from a clean environment and evaluated using the inherited official verifier together with augmented specification checks. The frozen main board contains 200 instances over 87 tasks; the remaining 85 instances form the development pool.

Release and governance

Traceability safeguards

These controls make the dataset auditable and reduce contamination or accidental answer leakage.

Traceability

  • Per-instance source task, model, scaffold, action count, and image mapping
  • Separate manifests for Terminal and Harbor acquisition lanes
  • Frozen development/test split with documented pre-freeze exposure
  • Failure-scene leak audits and source-failure replay evidence

Distribution

  • TrajRepair dataset layer declared CC BY 4.0
  • Repository code licensed separately
  • Upstream ownership, licenses, and citation obligations remain applicable
  • Evaluation-only canary embedded in examinee-facing artifacts
